마이크로서비스에서는 서비스가 잘게 쪼개지고 인스턴스가 여러 개 뜬다. 이때 **상태를 어디에 둘지**가 문제가 되는데, Redis가 그 공유 계층을 자주 맡는다.

> Redis 자체가 뭔지는 [Redis란](/wiki/redis-intro/), NoSQL 전반은 [NoSQL이란](/wiki/nosql/) 참고.

## 1. 공유 캐시 계층

각 서비스 인스턴스가 로컬 캐시만 쓰면 인스턴스마다 값이 달라진다. **외부 Redis를 공통 캐시**로 두면 모든 인스턴스가 같은 캐시를 본다. → 패턴은 [캐시 전략](/wiki/cache-strategy/).

## 2. 세션 · 토큰 스토어

인스턴스가 여러 개라 **세션을 메모리에 두면 요청마다 다른 서버로 가서 깨진다**(sticky session 의존). 세션·Refresh Token·블랙리스트를 Redis에 두면 어느 인스턴스로 가도 일관되게 인증된다. TTL로 만료까지 자동 처리.

## 3. 메시지 브로커 (Pub/Sub)

서비스 간 느슨한 통신을 위해 **Redis Pub/Sub**으로 이벤트를 발행/구독한다. 가볍고 빠르지만, 구독자가 없을 때 메시지가 사라지고 재전송·영속이 없다.

- 실시간 알림·간단한 브로드캐스트 → Pub/Sub로 충분.
- 유실 없는 처리·재처리가 필요하면 → **Redis Stream**(Consumer Group) 또는 Kafka 같은 전용 브로커.

## 전체 그림

> MSA에서 Redis는 보통 **"여러 인스턴스가 공유하는 빠른 상태 저장소"** 로 들어간다 — 캐시·세션·카운터처럼 빠르고 휘발 가능한 데이터에 강하고, 영구 원본은 여전히 DB에 둔다.
