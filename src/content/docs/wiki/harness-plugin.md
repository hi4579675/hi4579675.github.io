[하네스 엔지니어링](/wiki/harness-engineering/)이 "에이전트가 올바르게 일하도록 **환경을 설계하는 사고방식**"이라면, **Harness**는 그 설계를 **대신 해주는 클로드 코드 플러그인**입니다.

> **Harness** — *Agent Team & Skill Architect*. 한 줄 도메인 설명을 주면, 그에 맞는 **에이전트 정의 파일**과 **스킬 파일**을 자동 생성하는 메타 스킬.
>
> 깃허브: **[github.com/revfactory/harness](https://github.com/revfactory/harness)**

"메타 스킬"이라 부르는 이유가 여기 있습니다. 스킬을 만들어주는 스킬, 에이전트를 설계해주는 에이전트. 클로드 코드 생태계에서 다른 하네스를 *찍어내는* 상위 레이어(L3 Meta-Factory)에 위치합니다.

| | 하네스 엔지니어링 (개념) | Harness (플러그인) |
|---|---|---|
| 정체 | 환경 설계 *사고방식* | 그 환경을 자동 생성하는 *도구* |
| 비유 | "안장·고삐를 채운다는 발상" | "안장·고삐를 대신 만들어주는 공방" |
| 입력 | 사람이 직접 설계 | `"하네스 구성해줘"` 한 줄 |

---

## 핵심 기능 4가지

| 기능 | 하는 일 |
|---|---|
| **에이전트 팀 설계** | 6가지 아키텍처 패턴으로 팀 구조를 자동 설계 |
| **스킬 생성** | Progressive Disclosure 패턴으로 컨텍스트를 효율적으로 관리 |
| **오케스트레이션** | 에이전트 간 데이터 전달, 에러 핸들링, 팀 조율 |
| **검증 체계** | 트리거 검증 · 드라이 런 테스트 · 비교 테스트 |

> **Progressive Disclosure**가 왜 중요한가 — 에이전트가 모든 정보를 한 번에 읽으면 컨텍스트가 터집니다. 그래서 "지금 필요한 만큼만" 단계적으로 펼쳐 보여줍니다. [하네스 엔지니어링](/wiki/harness-engineering/) 글에서 다룬 *컨텍스트 불안* 문제를 구조적으로 막는 장치입니다.

데이터 전달도 한 가지가 아니라 **메시지 기반 · 태스크 기반 · 파일 기반**을 모두 지원하고, 단계마다 에러 핸들링과 폴백 전략이 끼어 있습니다.

## 산출물 구조

Harness를 실행하면 프로젝트 디렉토리에 이런 파일들이 생깁니다.

```text
.claude/
├── agents/
│   ├── analyst.md      # 분석 담당 에이전트 정의
│   ├── builder.md      # 구현 담당
│   └── qa.md           # 검증 담당
└── skills/
    ├── analyze/skill.md
    └── build/skill.md
```

`agents/`에는 각 에이전트의 역할·권한·트리거가, `skills/`에는 그 에이전트들이 실제로 쓰는 작업 절차가 들어갑니다.

### 전체 생성 흐름 (6단계)

```text
① 도메인 분석        → 무슨 일을 하는 프로젝트인가
② 팀 아키텍처 설계   → 에이전트 팀 vs 서브 에이전트 / 어떤 패턴
③ 에이전트 정의 생성 → .claude/agents/*.md
④ 스킬 생성          → .claude/skills/*/skill.md
⑤ 통합 & 오케스트레이션 → 에이전트 간 연결
⑥ 검증 & 테스트      → 트리거·드라이 런·비교
```

## 에이전트 팀 vs 서브 에이전트 — 뭘 고를까

| | 에이전트 팀 | 서브 에이전트 |
|---|---|---|
| 동작 | 여러 에이전트가 **역할을 나눠** 결과를 주고받음 | 하나가 **딱 한 번** 처리 |
| 권장 상황 | 단계가 있고, 결과를 다음으로 넘겨야 할 때 | 단발성 단순 작업 |
| 예시 | **코드 리뷰**: 아키텍처 분석 → 보안 검사 → 성능 검사 → 결과 통합 | 함수 하나 문서화 |

**모르겠으면 이 순서로 자문**하면 됩니다.

1. 결과물을 **다음 단계에 넘겨야** 하나? → 예면 팀 (파이프라인)
2. 동시에 **다른 관점에서 같은 걸** 봐야 하나? → 예면 팀 (팬아웃)
3. 그냥 **한 번 딱 하면 끝**이냐? → 예면 서브 에이전트

### 실제 판단 예시

| 작업 | 선택 | 이유 |
|---|---|---|
| 코드 리뷰 (아키/보안/성능) | 에이전트 팀 | 단계마다 결과를 넘김 |
| 함수 하나 문서화 | 서브 에이전트 | 단발성, 넘길 게 없음 |
| 버그 원인 후보 3개 동시 조사 | 에이전트 팀 | 같은 걸 여러 관점에서 |
| 변수명 일괄 변경 | 서브 에이전트 | 한 번에 끝 |

## 제일 재밌는 부분 — 6가지 아키텍처 패턴

작업의 "모양"에 맞춰 팀 구조를 고르는 게 Harness의 핵심입니다.

### ① 파이프라인 (Pipeline) — 일렬로 넘기기

```text
A → B → C → D
```

앞 단계의 결과가 다음 단계의 입력이 됩니다. **순서가 중요**할 때.
예: 코드 리뷰(분석 → 보안 → 성능 → 통합), 데이터 ETL.

### ② 팬아웃 / 팬인 (Fan-out / Fan-in) — 흩뿌렸다 모으기

```text
       ┌─ B ─┐
   A ──┼─ C ─┼── 통합
       └─ D ─┘
```

하나를 여러 갈래로 **동시에** 처리한 뒤 합칩니다. **독립적인 병렬 작업**에.
예: 파일 20개를 동시에 분석하고 리포트 하나로 합치기.

### ③ 전문가 풀 (Expert Pool) — 맞는 전문가 호출

```text
요청 → [라우터] → 적합한 전문가 1명 선택
        (보안가 / DB가 / 프론트가 ...)
```

여러 전문가 중 **상황에 맞는 사람만** 부릅니다. 작업 종류가 다양할 때.
예: 질문 성격에 따라 백엔드 / 프론트 / 인프라 전문가에게 라우팅.

### ④ 생성-검증 (Producer–Reviewer) — 만든 놈과 검사하는 놈 분리

```text
[생성자] → 결과 → [검증자] → (불합격 시 되돌림)
```

한 에이전트가 만들고, **다른 에이전트가 비판**합니다. 품질·정확성이 중요할 때.
예: 코드 생성 → 별도 에이전트가 테스트·리뷰 (적대적 검증).

### ⑤ 감독자 (Supervisor) — 매니저가 조율

```text
        [감독자]
        ↙  ↓  ↘
       W1  W2  W3
```

감독자가 워커들에게 일을 나눠주고 **결과를 보고 다음 지시**를 내립니다. 진행 중에 흐름이 동적으로 바뀌는 작업에.
예: "이 기능 만들어줘" → 감독자가 작업을 쪼개 분배.

### ⑥ 계층적 위임 (Hierarchical Delegation) — 트리 구조

```text
        [총괄]
        ↙    ↘
    [팀장A]   [팀장B]
     ↙ ↘      ↙ ↘
    W   W    W   W
```

감독자의 **다층 버전**입니다. 큰 작업을 부서 → 팀 → 개인으로 쪼갭니다. 대규모·복잡 프로젝트에.
예: 전체 마이그레이션을 모듈별 팀장에게, 팀장이 다시 파일별 워커에게.

## 패턴 선택 빠른 진단표

| 이 질문에 "예"라면 | 패턴 |
|---|---|
| 순서대로 결과를 넘겨야 한다 | **파이프라인** |
| 같은 일을 여러 개 동시에 처리하고 합친다 | **팬아웃 / 팬인** |
| 작업 종류에 따라 다른 전문가가 필요하다 | **전문가 풀** |
| 만든 결과를 따로 검증·비판해야 한다 | **생성-검증** |
| 진행 중에 동적으로 작업을 배분·조정해야 한다 | **감독자** |
| 너무 커서 여러 층으로 쪼개야 한다 | **계층적 위임** |

## 설치

```bash
git clone https://github.com/revfactory/harness.git
cp -r harness/skills/harness ~/.claude/skills/harness
```

이후 클로드 코드에서 `"이 프로젝트에 맞는 하네스 구성해줘"` 처럼 말하면, 위 6단계 흐름을 따라 도메인을 분석하고 팀을 설계해 `.claude/agents/`·`.claude/skills/`를 자동 생성합니다.

> 같은 저장소 계열에 **`revfactory/harness-100`** 도 있습니다 — 10개 도메인에 걸친 100개의 바로 쓰는 에이전트 팀 하네스(영어·한국어 합쳐 200패키지). 각 하네스는 4~5개의 전문 에이전트 + 오케스트레이터 스킬 + 도메인 스킬로 구성됩니다.

## 정리

> [하네스 엔지니어링](/wiki/harness-engineering/) 글이 **"왜·무엇을(개념)"** 이라면, Harness 플러그인은 그걸 **"어떻게(자동화)"** 실행하는 도구입니다.

"AI를 더 똑똑하게"가 아니라 "AI가 올바르게 일할 환경을 짠다"는 발상 — 그 환경을 한 줄로 찍어내는 게 Harness입니다. 어떤 작업이든, 먼저 그 **모양(순차냐·병렬이냐·검증이 필요하냐)**을 보고 6패턴 중 하나로 매핑하는 감각이 핵심입니다.
