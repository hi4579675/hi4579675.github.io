# 마이크로서비스 아키텍처로의 진화

*모놀리스에서 Spring Cloud 기반 MSA까지, 왜 그리고 어떻게 변화하는가*

---

## 1. 모놀리스 아키텍처 (Monolithic Architecture)

중소 규모의 웹 애플리케이션 대부분은 모놀리스 아키텍처 형태로 출발한다. 모놀리스란 애플리케이션의 모든 구성 요소(UI, 비즈니스 로직, 데이터베이스 액세스 등)를 하나의 코드베이스에 모아 단일 산출물로 빌드·배포하는 구조를 말한다. 프로젝트 초기에는 구조가 단순해서 개발 속도가 빠르고, 로컬 환경에서 디버깅이나 테스트도 수월하다.

### 1.1 장점

- **개발 시작이 빠르다** — 초기 구조가 단순해 프로토타이핑과 MVP 검증에 적합하다.
- **배포·운영이 단순하다** — 하나의 산출물만 빌드하면 되므로 파이프라인과 운영 절차가 간결하다.
- **디버깅·테스트가 쉽다** — 전체 코드가 한 곳에 있어 통합 테스트나 문제 추적이 비교적 수월하다.
- **인프라 비용이 낮을 수 있다** — 초기에는 여러 서비스·컨테이너를 운영하는 것보다 리소스 부담이 적다.

### 1.2 단점

- **확장성 한계** — 특정 기능만 스케일아웃하고 싶어도 전체 애플리케이션을 함께 확장해야 한다.
- **배포 위험 증가** — 작은 변경이 전체에 영향을 줄 수 있어, 배포 실패 시 전체 서비스 장애로 이어질 수 있다.
- **복잡도 누적** — 코드베이스가 커지면 모듈 간 경계가 흐려지고 스파게티 코드로 변질될 위험이 있다.
- **부분 장애가 전체 장애로 확대** — 한 컴포넌트의 버그나 메모리 누수가 전체 서비스에 영향을 줄 수 있다.

> 💡 **스케일아웃 (Scale-out)**: 서버 인스턴스를 수평으로 추가해 처리 능력을 확장하는 방식.

## 2. 마이크로서비스 아키텍처 (Microservices Architecture)

마이크로서비스 아키텍처는 모놀리스가 커지면서 드러나는 확장성·관리 문제에 대한 직접적인 대응으로 발전했다. 핵심 아이디어는 **분해(Decomposition)**와 **분리(Unbundling)**다. 대규모 코드베이스를 책임 단위의 작은 서비스로 나누고, 각 서비스가 독립적으로 개발·배포될 수 있도록 설계하는 것이다.

### 2.1 모놀리스 vs 마이크로서비스

| 구분 | 모놀리스 | 마이크로서비스 |
|------|----------|---------------|
| 배포 단위 | 전체 애플리케이션 단일 배포 | 서비스 단위 독립 배포 |
| 확장 방식 | 전체를 함께 스케일아웃 | 필요한 서비스만 개별 스케일아웃 |
| 기술 스택 | 하나의 기술 스택으로 통일 | 서비스별 최적 기술 선택 가능 |
| 장애 영향 | 부분 장애 → 전체 장애 가능 | 장애가 해당 서비스에 국한 |
| 팀 구조 | 하나의 큰 팀이 전체 담당 | 소규모 팀이 각 서비스 담당 |
| 초기 비용 | 낮음 | 상대적으로 높음 (인프라·운영) |

### 2.2 MSA로 얻을 수 있는 것

- **유연성(Flexible)** — 서비스가 분리되어 있어 변경 영향 범위가 작고, 테스트·배포가 빠르다.
- **회복성(Resilient)** — 한 서비스의 장애가 전체로 확산되지 않는다.
- **확장성(Scalable)** — 병목이 되는 서비스만 수평으로 확장할 수 있어 비용 효율이 높다.

> 💡 **Graceful Degradation**: 일부 기능에 장애가 생겨도 전체 서비스가 완전히 멈추지 않고 축소 운영되는 것.

## 3. Netflix의 MSA 전환 사례

Netflix는 MSA 전환의 가장 유명한 실제 사례다. 2000년대 후반, 단일 데이터베이스 장애 하나로 전체 서비스가 몇 시간 동안 멈추는 사고를 겪었다. 이를 계기로 모놀리스의 한계를 절감하고, 점진적으로 마이크로서비스로 전환하기 시작했다.

전환 과정에서 Netflix는 직접 인프라 도구들을 개발했다.

- **Eureka** — 서비스 디스커버리
- **Ribbon** — 클라이언트 사이드 로드밸런싱
- **Hystrix** — 서킷브레이커
- **Zuul** — API Gateway

이 도구들은 이후 오픈소스로 공개되었고, Spring Cloud Netflix라는 이름으로 Spring Cloud 생태계에 통합되었다. 현재는 일부(Ribbon, Hystrix)가 deprecated 되어 각각 Spring Cloud LoadBalancer, Resilience4j로 대체되고 있다.

## 4. Spring Cloud — MSA를 위한 도구 모음

Spring Cloud는 Spring Boot 위에서 마이크로서비스를 구축할 때 필요한 공통 패턴들을 구현해 놓은 프레임워크 모음이다.

| 기능 | Spring Cloud 모듈 |
|------|-------------------|
| 서비스 디스커버리 | Spring Cloud Netflix Eureka |
| 로드밸런싱 | Spring Cloud LoadBalancer + FeignClient |
| 서킷브레이커 | Resilience4j |
| API Gateway | Spring Cloud Gateway |
| 중앙 설정 관리 | Spring Cloud Config |
| 분산 추적 | Micrometer Tracing + Zipkin |
| 이벤트 드리븐 | Spring Cloud Stream (Kafka/RabbitMQ) |

## 5. 서비스 디스커버리 (Service Discovery)

마이크로서비스 환경에서는 서비스 인스턴스가 동적으로 생성·삭제된다. IP나 포트가 고정이 아니기 때문에, "주문 서비스가 지금 어디서 돌고 있지?" 같은 질문에 답해줄 누군가가 필요하다. 그게 서비스 디스커버리다.

### 동작 방식

1. 각 서비스 인스턴스가 시작될 때 디스커버리 서버에 자기 자신을 등록한다 (이름, IP, 포트 등).
2. 다른 서비스를 호출할 때 디스커버리 서버에 인스턴스 목록을 조회한다.
3. 인스턴스가 종료되면 목록에서 자동으로 제거된다.

Spring Cloud에서는 **Netflix Eureka**가 대표적인 서비스 디스커버리 서버다.

- **Eureka Server** — 서비스 레지스트리 역할. `@EnableEurekaServer` 하나로 띄울 수 있다.
- **Eureka Client** — 각 마이크로서비스에 붙으면 시작 시 자동으로 Eureka에 등록되고, 일정 주기로 하트비트를 보내 살아있음을 알린다.

> 💡 **서비스 레지스트리 (Service Registry)**: 현재 동작 중인 서비스 인스턴스들의 위치 정보(IP, 포트)를 관리하는 저장소. 일종의 전화번호부다.

> 💡 **하트비트(Heartbeat)**: 클라이언트가 주기적으로 "나 살아있어"라는 신호를 보내는 것. 신호가 끊기면 서버는 해당 인스턴스를 목록에서 제거한다.

## 6. 로드밸런싱 (Load Balancing)

네트워크 트래픽을 여러 서버로 분산시켜 부하를 줄이고, 시스템의 성능과 가용성을 높이는 기술이다. 특정 서버에 부하가 집중되는 것을 방지한다.

### 서버 사이드 vs 클라이언트 사이드

- **서버 사이드 로드밸런싱** — 클라이언트와 서버 사이에 별도의 로드밸런서(AWS ELB, Nginx)를 둔다.
- **클라이언트 사이드 로드밸런싱** — 호출하는 쪽(클라이언트)이 직접 인스턴스 목록을 들고 있다가 스스로 결정한다.

Spring Cloud에서는 **클라이언트 사이드 로드밸런싱**을 사용한다.

### Ribbon

Netflix가 개발한 클라이언트 사이드 로드밸런서. FeignClient에 통합되어 자동으로 로드밸런싱을 수행한다.

- **서버 리스트 제공자** — Eureka 등으로부터 서비스 인스턴스 리스트를 제공받아 사용
- **로드밸런싱 알고리즘** — 라운드 로빈, 가중치 기반 등 다양한 알고리즘 지원
- **Failover** — 요청 실패 시 다른 인스턴스로 자동 전환

### 로드밸런싱 알고리즘

| 알고리즘 | 설명 |
|---------|------|
| 라운드 로빈 | 각 서버에 순차적으로 요청 분배. 기본값 |
| 가중치 기반 | 서버 성능에 따라 가중치를 부여하고 비례하여 분배 |
| 최소 연결 | 현재 연결된 클라이언트 수가 가장 적은 서버로 요청 |
| 응답 시간 기반 | 서버의 응답 시간을 기준으로 가장 빠른 서버로 요청 |

### FeignClient

Spring Cloud에서 제공하는 HTTP 클라이언트로, 인터페이스와 어노테이션만으로 선언적으로 RESTful 웹 서비스를 호출할 수 있다. `@FeignClient(name = "product-service")`처럼 서비스 이름만 지정하면 Eureka에서 인스턴스 목록을 조회하고 Ribbon이 자동으로 로드밸런싱을 수행한다.

Order 서비스 1개, Product 서비스 인스턴스 3개가 있는 경우, FeignClient로 `product-service`를 호출하면 Ribbon이 Round Robin으로 3개 인스턴스에 순차적으로 요청을 분배한다.

> 💡 **Failover**: 요청이 실패했을 때 다른 인스턴스로 자동 전환. 하나의 인스턴스가 죽어도 서비스가 계속 동작한다.

## 7. 서킷브레이커 (Circuit Breaker)

서비스 A가 서비스 B를 호출하는데, B가 응답을 안 하면 어떻게 될까? A도 B를 기다리느라 멈추고, A를 호출한 쪽도 멈추고… 장애가 연쇄적으로 퍼진다. 이걸 **장애 전파(Cascading Failure)**라고 한다.

서킷브레이커는 전기 회로의 차단기처럼 동작한다. 문제가 생기면 회로를 끊어서 장애 전파를 막는다.

### 세 가지 상태

- **Closed (정상)** — 요청이 정상적으로 통과한다. 실패율을 모니터링한다.
- **Open (차단)** — 실패율이 임계치를 넘으면 회로를 연다. 이후 요청은 즉시 fallback으로 처리하고, 실제 서비스를 호출하지 않는다. (기본 20초 대기)
- **Half-Open (반개방)** — 대기 시간이 지나면 일부 요청만 시험 삼아 보내본다. 성공하면 Closed로 복구, 실패하면 다시 Open.

Spring Cloud에서는 **Resilience4j**가 표준이다. `@CircuitBreaker` 어노테이션으로 메서드 단위 적용이 가능하고, 실패 시 fallback 메서드를 지정해서 대체 응답을 줄 수 있다.

주요 설정 값:
- `slidingWindowSize: 5` — 최근 5번의 호출 결과로 판단
- `failureRateThreshold: 50` — 실패율 50% 초과 시 Open
- `waitDurationInOpenState: 20s` — Open 상태 유지 시간

> 💡 **Fallback**: 원래 호출이 실패했을 때 대신 실행되는 대체 로직. "B가 안 되면 이거라도 보여줘"라는 개념이다.

## 8. API Gateway

클라이언트(프론트엔드, 모바일 앱)가 수십 개의 마이크로서비스를 각각 직접 호출하면 클라이언트가 서비스 주소를 전부 알아야 하고, 인증도 서비스마다 따로 해야 한다. API Gateway는 모든 요청의 **단일 진입점(Single Entry Point)** 역할을 한다.

### 주요 역할

- **라우팅** — `/api/orders/**`는 주문 서비스로, `/api/products/**`는 상품 서비스로.
- **인증/인가** — 게이트웨이에서 한 번에 토큰 검증·권한 체크.
- **로드밸런싱** — 서비스 디스커버리와 연동하여 로드밸런싱 수행.
- **Rate Limiting** — 특정 클라이언트의 과도한 요청 제한.
- **로깅·모니터링** — 모든 트래픽이 한 곳을 지나므로 지표 수집이 편하다.

**Spring Cloud Gateway**는 **Predicate(조건)**와 **Filter(처리)** 조합으로 라우팅 규칙을 정의한다. Pre 필터에서 JWT 검증을, Post 필터에서 응답 가공을 처리하는 구조다. Eureka와 연동하면 `lb://service-name` 형태로 서비스 이름 기반 라우팅과 로드밸런싱이 자동으로 동작한다.

> 💡 Netty 기반 비동기·논블로킹으로 동작하여 높은 처리량을 제공한다. 이전의 Netflix Zuul을 대체한다.

## 9. 보안 구성 (OAuth2 + JWT)

MSA에서는 각 서비스가 독립적으로 배포되기 때문에 보안이 더 복잡해진다. 일반적인 패턴은 **API Gateway에서 인증을 처리**하고, 통과한 요청만 내부 서비스로 전달하는 것이다.

### OAuth2

OAuth2는 **토큰 기반**의 인증 및 권한 부여 프로토콜이다. 네 가지 역할을 정의한다: 리소스 소유자, 클라이언트, 리소스 서버, 인증 서버.

주요 Grant 방식:
- **Authorization Code Grant** — 인증 코드를 사용하여 액세스 토큰을 얻는 방식
- **Client Credentials Grant** — 클라이언트 자격 증명을 사용하여 서비스 간 통신에 활용

### JWT

JWT(JSON Web Token)는 사용자 정보를 담아 서명한 토큰이다. **헤더·페이로드·서명** 세 부분으로 구성된다.

- **자가 포함** — 토큰 자체에 모든 정보가 있어 별도 세션 저장이 필요 없다 (Stateless).
- **간결성** — 짧고 간결한 문자열로 URL, 헤더에 쉽게 포함된다.
- **서명 및 암호화** — 데이터의 무결성과 인증을 보장한다.

### MSA에서의 보안 흐름

별도의 **Auth Service**가 JWT를 발급하고, Gateway의 Pre 필터에서 토큰을 검증하는 패턴이 일반적이다. 사용자가 로그인하면 JWT를 발급받고, 이후 모든 요청에 JWT를 포함하여 Gateway에 전달한다. Gateway는 Pre 필터에서 토큰을 검증하고, 통과한 요청만 내부 서비스로 라우팅하며 실패 시 401을 반환한다. Spring Security를 STATELESS 세션 정책으로 설정하여 서버가 세션을 유지하지 않도록 한다.

## 10. Config Server (중앙 집중식 구성 관리)

마이크로서비스가 늘어나면 각 서비스의 설정 파일(DB 접속 정보, API 키 등)을 일일이 관리하는 게 어렵다. **Spring Cloud Config**는 설정을 한 곳에서 관리하고, 서비스가 기동할 때 또는 런타임 중에 가져가도록 한다.

### 주요 기능

- **중앙 집중식 구성 관리** — 모든 마이크로서비스의 설정을 중앙에서 관리.
- **환경별 구성** — 개발(dev), 스테이징, 운영(prod) 환경별로 설정 분리. `application-dev.yml`, `application-prod.yml` 형태로 관리.
- **실시간 구성 변경** — 설정 변경 시 애플리케이션을 재시작하지 않고 반영 가능.

Config 서버는 Git 저장소에서 설정 파일을 읽어와 HTTP API로 제공한다. 각 마이크로서비스는 시작 시 Config Server에서 자신의 설정을 가져온다. `@EnableConfigServer` 어노테이션 하나로 Config 서버를 활성화할 수 있다.

### 실시간 구성 변경 방법

- **Spring Cloud Bus** — Kafka나 RabbitMQ를 통해 변경 사항을 모든 클라이언트에 자동 전파.
- **`/actuator/refresh`** — 클라이언트의 해당 엔드포인트를 POST 호출하면 수동으로 갱신.
- **Git 저장소 연동** — 설정 파일의 버전 관리와 변경 이력 추적.

## 11. 분산 추적 (Distributed Tracing)

모놀리스에서는 로그를 한 곳에서 보면 됐다. MSA에서는 하나의 요청이 여러 서비스를 거쳐간다. "어디서 느려진 거야?", "어느 서비스에서 에러가 난 거야?"를 추적하려면 요청의 흐름을 end-to-end로 볼 수 있어야 한다.

### 핵심 개념

- **Trace** — 하나의 요청이 시스템을 통과하는 전체 여정. 고유한 Trace ID를 가진다.
- **Span** — Trace 안에서 각 서비스가 수행한 개별 작업 단위. 부모-자식 관계로 호출 계층 구조를 표현한다.
- **Context** — 서비스 간에 전파되는 Trace ID, Span ID 등의 정보.

**Micrometer Tracing**이 자동으로 Trace ID와 Span ID를 생성·전파한다. 서비스 간 호출 시 HTTP 헤더에 실어 보내기 때문에 전체 흐름이 연결된다.

**Zipkin**은 트레이스 데이터를 수집하고 시각화하는 도구다. 서비스 간 호출 관계와 각 스팬의 소요 시간을 타임라인으로 볼 수 있어, 성능 병목이 발생하는 부분을 바로 식별할 수 있다.

> 💡 **샘플링(Sampling)**: 모든 요청을 추적하면 성능에 영향을 준다. 개발 환경에서는 100%, 운영에서는 비율을 낮춰 적용한다.

## 12. 이벤트 드리븐 아키텍처 (Event-Driven Architecture)

MSA에서 서비스 간 통신은 크게 두 가지다. **동기(HTTP 호출)**와 **비동기(이벤트)**. 동기 호출만으로 처리하면 호출 대상 서비스가 죽으면 호출하는 쪽도 영향을 받는 강한 결합이 생긴다.

이벤트 드리븐은 이벤트를 발행하고, 관심 있는 서비스가 알아서 구독·처리하는 방식이다.

### 주요 개념

- **이벤트** — 시스템 내에서 발생하는 상태 변화나 행동을 나타내는 메시지.
- **이벤트 소스** — 이벤트를 생성하여 이벤트 버스에 전달.
- **이벤트 핸들러** — 이벤트를 수신하여 처리.
- **이벤트 버스** — 이벤트 소스와 핸들러 간의 메시지 전달을 중개 (Kafka, RabbitMQ).

### 장점과 단점

**장점**
- **느슨한 결합** — 서비스 간 강한 종속성을 제거하여 독립적인 개발·배포 가능.
- **확장성** — 이벤트 프로듀서와 컨슈머를 독립적으로 확장 가능.
- **비동기 처리** — 이벤트를 비동기적으로 처리하여 시스템 응답성 향상.

**단점**
- **복잡성 증가** — 이벤트 흐름과 상태 관리를 체계적으로 설계해야 한다.
- **장애 전파** — 이벤트 실패 시 다른 서비스로 장애가 전파될 수 있다. 재처리 및 복구 메커니즘이 필요하다.

### 실제 예시: 온라인 쇼핑몰 주문

주문 서비스가 '주문 생성' 이벤트를 발행하면, Kafka나 RabbitMQ가 이 이벤트를 구독 중인 서비스들에 전달한다. 재고 서비스는 재고를 확인·차감하고, 배송 서비스는 배송 준비를 시작한다. 이 모든 과정이 병렬로 처리된다.

**Spring Cloud Stream**은 Kafka, RabbitMQ 등의 메시지 브로커와 통합하여 이벤트 드리븐 마이크로서비스를 구축하기 위한 프레임워크다. 바인더 추상화를 통해 브로커가 바뀌어도 애플리케이션 코드 변경을 최소화할 수 있다.

## 13. MSA, 무조건 도입해야 할까?

MSA를 도입하기 위해서는 서비스 디스커버리, 로드밸런싱, 서킷브레이커, API Gateway, 설정 관리, 분산 추적 등 많은 것들이 필요하다.

빠르게 프로토타입을 만들어야 한다면 **모놀리식으로 시작하고, 필요한 시점에 부분 전환**하는 것도 충분히 유효한 전략이다.

Spring Cloud가 아닌 다른 프레임워크로 MSA를 개발하더라도, 위에서 다룬 기능들의 역할은 동일하게 필요하다. 도구가 달라도 개념은 같다.

### Spring Cloud vs Kubernetes

MSA 인프라 관점에서 자주 비교되는 도구가 쿠버네티스(Kubernetes)다.

| 구분 | Spring Cloud | Kubernetes |
|------|-------------|------------|
| 초점 | 애플리케이션 레벨 (서비스 통신, 디스커버리) | 인프라 레벨 (컨테이너 배포, 스케일링) |
| 서비스 디스커버리 | Eureka | Kubernetes Service + DNS |
| 설정 관리 | Spring Cloud Config | ConfigMap, Secret |
| 로드밸런싱 | Spring Cloud LoadBalancer | kube-proxy, Ingress |

둘은 상호 보완적인 관계다. **Spring Cloud Kubernetes**를 사용하면 두 세계를 통합하여 사용할 수도 있다. Netflix, Google, Airbnb 등이 쿠버네티스 기반의 대규모 MSA를 운영하고 있다.

## 정리

| 컴포넌트 | 역할 | Spring Cloud |
|----------|------|--------------|
| 서비스 디스커버리 | 서비스 위치 동적 관리 | Eureka |
| 로드밸런싱 | 트래픽 분산 | Spring Cloud LoadBalancer + FeignClient |
| 서킷브레이커 | 장애 전파 차단 | Resilience4j |
| API Gateway | 단일 진입점, 인증 | Spring Cloud Gateway |
| 보안 | JWT 발급·검증 | Spring Security + OAuth2 |
| 설정 관리 | 중앙 집중식 설정 | Spring Cloud Config |
| 분산 추적 | 서비스 간 요청 흐름 추적 | Micrometer Tracing + Zipkin |
| 이벤트 드리븐 | 비동기 서비스 간 통신 | Spring Cloud Stream (Kafka/RabbitMQ) |
