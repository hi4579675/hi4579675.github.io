> 티켓팅 대기열을 Redis로 설계하면서 마주친 8가지 우회 시나리오 — 새로고침 어뷰징부터
> FIFO가 100% 보장되는가라는 질문까지. 시스템이 어디까지 막고, 어디서부터 못 막는지를 정리한다.

---

## 왜 이 글을 쓰는가

한국시리즈 1차전 티켓 오픈 시점에 5만 명이 동시에 좌석 선택 페이지에 접근한다고 가정하자.

대기열 없이 이 트래픽을 직접 받으면 세 가지 문제가 동시에 터진다.

1. 좌석 점유 로직의 락 경합으로 처리량이 0에 수렴한다
2. 빠른 네트워크를 가진 사람이 늦게 들어와도 먼저 좌석을 잡는 불공정이 발생한다
3. 새로고침할 때마다 순번이 밀리는 — 기존 티켓팅 사이트의 악명 — 이 재현된다

이 문제를 풀기 위해 Redis 기반 대기열을 설계했다. 설계를 마친 후 스스로 물었다. "이걸 우회하려는 사람은 어떻게 시도할까?" 그 답이 이 글이다.

---

## 시스템 개요

본론 전에 구조를 빠르게 짚고 넘어간다.

**두 상태의 분리가 핵심이다.**

| 상태 | 의미 |
|---|---|
| 대기 중 (Waiting) | 줄 서있음. 좌석 페이지 접근 불가 |
| 입장 허가 (Admitted) | 토큰을 받은 상태. 좌석 페이지 접근 가능 |

**Redis에는 5개의 키가 있다.**

```
waiting:queue:{gameId}            → Sorted Set  (줄 그 자체)
waiting:user:{gameId}:{userId}    → Hash        (사용자 메타데이터)
waiting:cursor:{gameId}           → String      (어디까지 호출했는지 책갈피)
admission:token:{token}           → String TTL  (진입 토큰)
admission:user:{gameId}:{userId}  → String TTL  (토큰 역참조)
```

**흐름은 단순하다.**

```
사용자 진입 → Sorted Set에 timestamp score로 추가
         ↓
워커(1초마다) → cursor 기준 다음 N명 조회 → 토큰 발급
         ↓
사용자 폴링 → 토큰 수령 → 좌석 페이지 진입
         ↓
좌석 점유 API → 토큰 검증 → 통과 시 좌석 락
```

좌석 점유 API는 `X-Admission-Token` 헤더를 필수로 받는다. 토큰 없이는 401이다.

## 8가지 우회 시도

### 시나리오 1: 새로고침으로 순번을 앞당길 수 있나?

**공격:** 순번이 안 좋자 새로고침으로 새 진입 시각을 받으려 한다.

**방어:**

```redis
ZADD waiting:queue:42 NX 1712486400123 "user:100"
```

`NX`(Not eXists) 옵션이 전부다. 이미 존재하는 member는 score를 덮어쓰지 않는다. 새로고침해도 처음 진입 시각이 그대로 유지된다.

이 한 글자가 시스템의 공정성 전체를 떠받친다. 빠지면 새로고침할수록 순번이 뒤로 밀리는 — 기존 티켓팅 사이트의 그 현상 — 이 그대로 재현된다.

**검증:** 같은 userId로 ZADD를 두 번 호출한 뒤 ZSCORE로 score가 첫 번째 값과 동일한지 확인한다.

---

### 시나리오 2: URL을 알아내 좌석 API를 직접 호출

**공격:** 대기열을 거치지 않고 `POST /api/games/42/seats/15/hold`를 직접 호출한다.

**방어:**

좌석 점유 API는 `X-Admission-Token` 헤더를 필수로 받는다. 헤더가 없으면 즉시 401이다. 토큰은 워커만 발급할 수 있고, 워커는 cursor 기반으로 순서대로만 호출하므로 임의 발급이 불가능하다.

원리는 단순하다. **"URL을 안다(지식)"와 "토큰을 가진다(권한)"를 분리**한 것이다. 시스템의 어떤 부분을 알아도, 추가적인 권한 증명이 없으면 들어갈 수 없다.

**검증:** 진입 토큰 없이 좌석 API 호출 → 401 반환.

---

### 시나리오 3: 다른 사람의 토큰을 탈취해 사용

**공격:** XSS 등으로 다른 사용자의 진입 토큰을 탈취해 자신의 요청에 붙인다.

**방어:**

좌석 점유 API는 두 가지를 교차 검증한다.

1. `Authorization: Bearer {jwt}` → JWT에서 사용자 ID 추출
2. `X-Admission-Token: {token}` → Redis에서 토큰의 사용자 ID 조회

둘이 일치하지 않으면 401이다.

```
JWT의 userId = user:200  (공격자 본인)
토큰의 userId = user:100 (피해자)
→ 불일치 → 401
```

공격자가 피해자의 JWT까지 탈취하지 않는 한 통하지 않는다.

**한계:** JWT까지 같이 탈취당하면 막을 수 없다. 그건 인증 시스템이 뚫린 것으로, 대기열 시스템의 책임 영역 밖이다. 이 경계를 명확히 하는 것 자체가 설계의 일부다.

---

### 시나리오 4: 여러 탭을 열어 동시 진입 시도

**공격:** 5개 탭을 열어 5번 진입을 시도한다. 좋은 순번을 받으면 그쪽으로 가겠다는 심산이다.

**방어:**

`ZADD NX`로 같은 userId는 한 번만 등록된다. 5개 탭에서 동시에 시도해도 Redis 큐에는 1번만 들어간다. 모든 탭이 동일한 순번을 받는다.

**의도치 않은 보너스:** 5개 탭 모두 같은 토큰을 받으므로, 어느 탭에서 좌석을 잡든 동작한다. 사용자 입장에서는 오히려 편하다.

시스템이 사용자를 바라보는 단위가 세션도 탭도 기기도 아닌, **userId**라는 점이 일관성을 만든다.

---

### 시나리오 5: 입장 후 결제 타임아웃

이건 공격이 아니라 정상 시나리오다. 하지만 시스템이 어떻게 처리하는지가 설계 품질을 보여준다.

**상황:** 좌석을 잡고 결제 페이지로 넘어갔는데, 카드 인증이 실패했다. 시간이 흘렀다.

**처리:** 두 개의 TTL이 분리되어 있다.

| 자원 | TTL | 의미 |
|---|---|---|
| 진입 토큰 | 15분 | 좌석 페이지에 머무를 권리 |
| 좌석 점유 락 | 7분 | 특정 좌석을 잡아두는 권리 |

좌석 락(7분)이 만료되면 좌석은 풀린다. 하지만 진입 토큰(15분)은 살아있다. 사용자는 좌석 페이지로 돌아와 다른 좌석을 시도할 수 있다.

두 자원의 수명을 분리한 이유는 간단하다. **좌석을 한 번 놓쳤다고 대기열을 다시 타는 건 너무 가혹하다.** 동시에 토큰이 무한히 유효하면 시스템 처리량이 떨어진다. 15분이라는 경계가 "얼마나 너그러울 것인가"의 답이다.

---

### 시나리오 6: Redis가 죽으면?

**상황:** 단일 Redis 인스턴스가 응답하지 않는다.

솔직히 말하면, 단일 인스턴스는 SPOF(Single Point of Failure)다. Redis가 죽으면 대기열 시스템 전체가 정지한다. 이건 명백한 한계다.

**그나마 덜 망하기 위한 원칙:**

첫째, **안전 측 실패(Fail-Safe)**. 토큰 검증이 실패하면 좌석 점유를 허용하지 않는다. "Redis가 죽었으니 일단 통과시키자"는 절대 안 된다. 그러면 대기열을 우회한 5만 명이 동시에 좌석 로직을 때려서 진짜로 서버가 터진다.

둘째, **데이터 손실은 감수한다.** 대기열 데이터는 휘발성이다. Redis가 살아나면 사용자들이 재진입해서 새 줄을 만든다. 영구적인 피해는 없다. 영구 데이터(결제 등)는 MySQL에 있다.

**한계:** 복구 후 기존 순번은 보존되지 않는다.

**프로덕션 개선안 (본 프로젝트 범위 외):** Redis Sentinel 또는 Cluster로 고가용성 구성. 진입 시각을 클라이언트 쿠키에도 저장해두면 복구 후 순번 보존도 어느 정도 가능하다.

---

### 시나리오 7: 대기열 진입 API 자체를 DDoS로 폭주

**공격:** 봇이 분당 수십만 요청으로 `POST /api/games/{gameId}/waiting/enter`를 때린다.

**방어 (애플리케이션 레벨):**

- IP 기반 Rate Limiting. 한 IP가 분당 N회 이상 시도 시 차단. Spring Cloud Gateway나 Bucket4j로 구현 가능하다.
- 같은 userId의 중복 등록은 `ZADD NX`로 Redis 레벨에서 차단된다. 큐 무결성은 유지된다. 다만 요청 처리 자체의 CPU 부담은 있다.

**막을 수 없는 것:**

분산 봇넷(전 세계 IP에서 조금씩)은 IP 차단으로 못 막는다. IP당 5번씩만 보내면 정상 사용자와 구분이 안 된다.

**프로덕션 개선안:** AWS WAF, CloudFront, CAPTCHA. 이건 인프라 레벨의 방어로, 애플리케이션 레벨과 다른 층이다. 본 프로젝트는 애플리케이션 레벨까지만 다룬다.

---

### 시나리오 8: FIFO가 정말 100% 보장되는가?

**짧은 답: 아니다.**

두 가지 이유로 100%는 불가능하다.

**첫째, 동일 ms 충돌.** 두 사용자가 같은 밀리초에 진입하면 score가 동일해진다. Redis Sorted Set은 score가 같으면 member를 사전순으로 정렬한다. 결정적이긴 하지만, 클라이언트가 실제로 버튼을 누른 순서와는 무관하다.

**둘째, 네트워크 지연 차이.** 사용자 A가 0.001초 먼저 버튼을 눌렀어도, A의 인터넷이 느리면 서버에 늦게 도착한다. 서버는 도착 시각만 알 수 있다. 서버 기준 FIFO는 보장되지만, 사용자 기준 FIFO는 보장되지 않는다.

**현실적 보장:** "ms 단위 정렬, 동일 ms 내 미세 역전 허용". 목표는 "FIFO 위반 5% 이내"다.

100% FIFO를 보장하려면 모든 요청이 단일 노드의 단일 스레드에서 한 줄로 처리되어야 한다. 그건 분산 환경과 본질적으로 충돌한다. 분산은 곧 병렬이고, 병렬은 순서의 일부 포기다. 트레이드오프다.

"충분히 공정한 정렬을 통계적으로 보장한다"가 현실적인 목표다. 100%를 주장하는 시스템보다 이 한계를 인정하는 시스템이 더 믿을 만하다.

## 정리

8개 시나리오를 관통하는 두 가지 원칙이 있다.

**첫째, 작은 디테일이 큰 보장을 만든다.** `ZADD NX`의 두 글자가 공정성 전체를 떠받친다. `X-Admission-Token` 헤더 하나가 우회 경로를 차단한다. 설계는 거창한 것이 아니라 이런 결정들의 집합이다.

**둘째, 어디까지 막고 어디서부터 못 막는지를 명확히 한다.** JWT 탈취는 인증 시스템의 책임이다. 분산 봇넷은 인프라 레벨의 책임이다. Redis 단일 인스턴스의 SPOF는 인정된 한계다. 경계를 명확히 하지 않으면 시스템이 무엇을 보장하는지 아무도 알 수 없다.

모든 공격을 막는 시스템은 없다. 어떤 공격을 막고 어떤 공격을 감수하는지 알고 설계하는 것이 전부다.
