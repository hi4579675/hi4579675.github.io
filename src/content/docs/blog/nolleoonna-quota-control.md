외부 관광 API 파이프라인을 운영하면, 가장 먼저 부딪히는 건 성능이 아니라 **호출 한도**다.
놀러온나 파이프라인도 TourAPI 일일 제한(공식 1,000콜) 안에서 부산 ~7,000 스팟을 안정적으로 적재해야 했다.

핵심 질문은 하나였다.

> "어떻게 하면 누락 없이, 한도 내에서, 매일 돌릴 수 있을까?"

이 글은 우리가 적용한 **4단계 비용 통제 전략**을 정리한 기록이다.

---

## 1. 제약: 1,000콜 제한 + 도메인 우선순위

TourAPI 스팟 동기화는 단순 조회가 아니다.

- 목록 API 1회
- 변경 건마다 상세 API 4회 (`detailCommon2 / Intro2 / Info2 / Image2`)

즉, 변경 건 1개 처리에 사실상 **최대 5콜**이 든다.

운영에서 우리는 공식 한도 1,000콜보다 낮은 **내부 한도 900**을 둔다.
장애 재시도/운영자 수동 실행을 위한 100콜 버퍼를 남기기 위해서다.

또한 스팟은 3개 타입(12 관광지 / 14 문화시설 / 39 음식점)을 동시에 다뤄야 하므로,
"어떤 타입부터 얼마나 쓸지"도 정책이 필요했다.

---

## 2. 실패 시나리오: 무지성 full scan의 비용 폭발

가장 단순한 방식은 "매일 전체를 다시 긁는 것"이다.

부산 7,000 스팟 × 4 endpoint = **28,000콜**.
1,000콜 제한이면 **단순 부트스트랩에 28일** 걸리는 구조다.

문제는 비용만이 아니다.

- 중간에 예산이 끊기면 "어디까지 했는지" 추적 불가
- 다음날 또 처음부터 돌다가 같은 구간에서 또 끊김
- 결국 비용도 낭비, 데이터도 불안정

특히 **순차 처리**일 때 `contentTypeId=12`에만 quota 다 쓰면 14·39는 영원히 못 들어가는 starvation도 발생한다.

---

## 3. 4단계 방어 전략

### 3-1. 변경 감지 — 수정시각이 같으면 상세 호출 생략

첫 번째 방어선은 `modifiedtime` 비교다.

목록 API 응답에 이미 각 스팟의 `modifiedtime`이 들어 있다.
이걸 DB의 `source_modified_time`과 비교해서 같으면 **상세 4콜을 통째로 skip** 한다.

```python
list_modified = parse_tourapi_timestamp(item["modifiedtime"])
db_modified = await repo.get_source_modified_time(content_id)
if db_modified and list_modified and db_modified >= list_modified:
    return  # detail 4콜 절약
```

이 한 단계로 대부분의 "변경 없음" 데이터를 초반에 제거한다.
실제로 비용 절감의 체감 효과가 가장 크다.

### 3-2. 워터마크 break + bootstrap_complete 게이팅

두 번째 방어선은 **페이지 단위 조기 종료**다.

`arrange=C`(수정일 역순)로 정렬하면 첫 페이지가 가장 최근에 수정된 건들.
**페이지 전체가 "변경 없음"이면 그 뒤 페이지는 더 과거 데이터**라서, 더 이상 볼 필요 없이 즉시 break해도 누락 없다.

```python
if not bootstrap_mode and page_unchanged_count == len(items):
    return False, True  # 워터마크 안전 종료
```

⚠️ **함정이 하나 있다.** 이 최적화를 무방비로 켜두면 부트스트랩이 막힌다.

> 14번째 cron 실행에서 `records_fetched=0`이 찍혔다.
> page 1의 5건이 모두 어제 sync된 거라 break이 떨어지고, page 2 이후 6,950건은 **한 번도 본 적 없는데 평생 누락**.
> 부트스트랩 미완 상태에선 "page 1 unchanged"가 "전체 unchanged"를 의미하지 않았다.

해결: `bootstrap_complete` 플래그 게이팅.
모든 타입의 cursor가 마지막 페이지에 도달한 시점에만 `bootstrap_complete=true`로 전환하고, 그 전엔 unchanged 페이지를 만나도 다음 페이지로 진행한다.

→ **비용 최적화는 운영 단계(bootstrap vs 정상)에 따라 의미가 달라진다.**

### 3-3. 타입별 예산 배분 — 12/14/39에 균형 있게

세 번째 방어선은 **타입별 예산 관리**다.

```python
TYPE_BUDGET_WEIGHTS = {"12": 0.5, "14": 0.25, "39": 0.25}
# 12(관광지) 450 / 14(문화시설) 225 / 39(음식점) 225
```

가중치 근거: 부산 기준 contentTypeId=12 양이 14·39 합친 것보다 많아 0.5 비중. 14·39는 비슷한 수라 동률.

이 정책이 없으면 한 타입이 예산을 다 먹고, 다른 타입은 며칠째 동기화가 밀리는 starvation이 생긴다.

핵심은 "총 예산 통제"뿐 아니라 **"도메인 신선도 균형"**이다.
어제 영화관 정보가 갱신됐는데 오늘 그게 코드에 안 들어와 있으면 사용자에겐 동일한 stale 경험이다.

### 3-4. 커서 기반 재개 — 끊겨도 다음 회차가 이어받는다

네 번째 방어선은 **중단 지점의 명시적 저장**이다.

예산 초과 직전에 다음 정보를 `SYNC_LOGS.metadata`에 저장한다.

```python
next_cursor_by_type = {
    "12": {"page": 5, "content_id": "126128", "modifiedtime": "20260427173010"},
    "14": {"page": 2, "content_id": "208938", "modifiedtime": "20260427162708"},
    "39": {"page": 3, "content_id": "298099", "modifiedtime": "20260422142557"},
}
```

다음 실행은 이 cursor에서 이어받는다.
"매일 처음부터"가 아니라 **"끊긴 지점부터"** 처리하므로, 같은 API 콜을 반복 소모하지 않는다.

운영 상태 추적용으로 같이 저장되는 metadata 필드:

| 필드 | 의미 |
|---|---|
| `stopped_by_budget` | 예산 컷으로 중단됐는지 |
| `next_cursor_by_type` | 타입별 다음 시작 지점 |
| `api_calls_by_type` | 타입별 누적 호출 수 |
| `terminal_page_by_type` | 타입별 마지막 페이지 도달 여부 |
| `bootstrap_complete` | 모든 타입이 마지막 페이지 도달했는지 |

이 정보가 있어야 "왜 오늘 일부만 들어왔는지"를 설명할 수 있고, 다음 회차에서 자동 복원이 가능하다.

> 파이프라인은 코드보다 운영이 길다.
> metadata는 그 운영을 지탱하는 **로그 계약**이다.

---

## 4. 운영 결과: 호출 통제 + 처리량 유지 + 누락 방지

이 4단계를 적용하면 세 가지가 동시에 달성된다.

| 목표 | 달성 방식 |
|---|---|
| 호출 수 통제 | 일 예산 900콜 + 타입별 분할로 안정적 동작 |
| 처리량 유지 | 변경 건 중심으로 콜을 써서 실효 효율 상승 |
| 누락 방지 | 중단 지점부터 재개 + bootstrap 게이팅으로 데이터 공백 최소화 |

즉, "많이 호출해서 최신성 확보"가 아니라
**"정확히 필요한 만큼만 호출해서 최신성 유지"** 하는 구조가 된다.

---

## 5. 남은 리스크와 다음 단계

아직 풀어야 할 과제도 있다.

- 트래픽/이벤트 급증일의 예산 재조정 자동화
- 타입별 동적 가중치 (고정 0.5 / 0.25 / 0.25의 한계)
- 통합 테스트 고도화 (testcontainers 기반 SQL 검증)
- 혼잡도/LLM 파이프라인과 예산 정책의 통합 최적화

다음 단계의 목표는 단순 절약이 아니라,
**비용·신선도·SLA를 동시에 만족하는 적응형 제어**다.

---

## 마무리

일일 1,000콜 제한은 제약이지만, 동시에 **설계를 성숙하게 만드는 압력**이다.
놀러온나에서는 이 제약 덕분에 다음 4가지 원칙이 생겼다.

1. **변경만 처리한다**
2. **예산은 타입별로 통제한다**
3. **중단은 실패가 아니라 상태다**
4. **상태는 metadata로 남겨 다음 실행이 복원한다**

결국 좋은 파이프라인은 "빨리 도는 코드"가 아니라
**제약 안에서 매일 같은 품질을 내는 운영 시스템**이었다.
