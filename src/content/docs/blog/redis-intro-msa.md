> 왜 레디스 같은 NoSQL이 등장했는지, 마이크로서비스 시대에 레디스가 핵심 인프라가 된 이유를 정리한다.

---

## 1.1 NoSQL의 등장 배경

### 모놀리틱 아키텍처

모놀리틱 아키텍처(Monolithic Architecture)란 애플리케이션의 모든 기능이 **하나의 거대한 코드베이스와 하나의 실행 단위**로 묶여 있는 전통적인 소프트웨어 구조다.

초창기 전자상거래 사이트를 떠올려보자. 회원가입부터 상품 조회, 장바구니, 결제, 배송 추적까지 모든 기능이 하나의 WAR 파일로 패키징되어 톰캣 위에서 동작했다. 데이터는 MySQL이나 Oracle 같은 하나의 관계형 데이터베이스에 저장되었다.

개발 초기에는 단순하고 빠르게 만들 수 있다는 장점이 있다. 하지만 서비스가 성장할수록 문제가 생긴다.

- 작은 기능 하나를 수정해도 **전체 애플리케이션을 다시 빌드하고 배포**해야 한다
- 특정 기능에만 트래픽이 몰려도 **전체 서버를 확장**해야 한다
- 코드베이스가 거대해질수록 유지보수가 어려워지고, **장애 발생 시 전체 서비스가 멈춘다**

### 마이크로서비스 아키텍처

이러한 한계를 극복하기 위해 등장한 것이 마이크로서비스 아키텍처(MSA)다. 하나의 거대한 애플리케이션을 **작고 독립적인 여러 개의 서비스로 분리**하는 방식이다.

전자상거래 사이트를 MSA로 재구성하면 다음과 같이 나뉜다.

| 서비스 | 역할 | 사용 데이터 |
|--|--|--|
| 회원 서비스 | 회원가입, 인증, 프로필 관리 | 사용자 정보 |
| 상품 서비스 | 상품 등록, 검색, 카테고리 관리 | 상품 카탈로그 |
| 주문 서비스 | 주문 생성, 상태 관리 | 주문 내역 |
| 결제 서비스 | 결제 처리, 환불 | 결제 트랜잭션 |
| 배송 서비스 | 배송 추적, 배송지 관리 | 배송 로그 |

각 서비스는 서로 다른 팀이 서로 다른 언어와 데이터베이스로 개발할 수 있다. 회원 서비스는 MySQL, 상품 서비스는 Elasticsearch, 장바구니 서비스는 레디스를 쓰는 식이다. 이것을 **폴리글랏 퍼시스턴스(Polyglot Persistence)** 라고 부른다.

### 데이터 저장소 요구 사항의 변화

MSA로 전환되면서 데이터 저장소에 대한 요구가 근본적으로 달라졌다.

| 과거 (모놀리틱) | 현재 (MSA) |
|--|--|
| 하나의 RDBMS로 충분 | 서비스마다 다른 저장소 필요 |
| 정형 데이터 중심 | JSON, 그래프, 키-값 등 다양한 형태 |
| 초 단위 응답 허용 | 밀리초 단위 응답 필수 |
| 수직 확장 (Scale-Up) | 수평 확장 (Scale-Out) |
| 단일 서버 | 분산 환경, 다중 리전 |

이러한 새로운 요구를 만족시키기 위해 등장한 것이 **NoSQL 데이터베이스**다.

## 1.2 NoSQL이란

NoSQL은 **'Not Only SQL'** 의 약자로, 관계형 데이터베이스의 한계를 보완하기 위해 등장한 데이터베이스의 총칭이다. 단일 기술이 아니라, 관계형 모델을 따르지 않는 다양한 데이터베이스를 묶어 부르는 용어다.

### 핵심 특징

**실시간 응답**

메모리 기반으로 동작하거나 인덱싱을 극도로 최적화하여 **밀리초 단위 응답**을 제공한다. 트위터의 타임라인, 게임의 실시간 랭킹 등이 이에 해당한다.

**수평적 확장성 (Scale-Out)**

RDBMS는 주로 수직 확장(서버 스펙 업그레이드)에 의존한다. 비용이 기하급수적으로 늘어나며 한계가 명확하다.

NoSQL은 수평 확장을 기본 전제로 설계되었다. 서버를 여러 대로 늘려서 데이터를 분산 저장하는 방식이다.

```
수직 확장 (Scale-Up):
  서버 1대의 CPU/RAM을 계속 업그레이드 → 비용 ↑, 한계 존재

수평 확장 (Scale-Out):
  서버 1대 → 2대 → 4대 → 8대 ... → 이론적으로 무한 확장
  각 서버가 데이터의 일부를 나눠서 저장 (샤딩)
```

**고가용성 (High Availability)**

데이터를 여러 노드에 복제(replication)하여 저장한다. 한 노드에 장애가 생겨도 다른 노드가 즉시 역할을 대신한다.

```
          ┌──────────┐
          │  Master   │  ← 쓰기
          └────┬──┬───┘
               │  │
       ┌───────┘  └───────┐
       ▼                  ▼
  ┌──────────┐      ┌──────────┐
  │ Replica 1│      │ Replica 2│  ← 읽기 / 장애 시 승격
  └──────────┘      └──────────┘
```

**클라우드 네이티브**

AWS ElastiCache, Google Memorystore, Azure Cache 등 관리형 서비스로 제공된다. 컨테이너 배포, 오토 스케일링과 자연스럽게 통합된다.

**스키마 유연성**

RDBMS는 테이블 생성 시 스키마(컬럼 구조)를 미리 정의해야 하고, 변경이 쉽지 않다. NoSQL은 스키마리스(Schemaless) 또는 유연한 스키마를 지원하여 필드를 자유롭게 추가하거나 변경할 수 있다.

### RDBMS vs NoSQL 비교

| 항목 | RDBMS | NoSQL |
|--|--|--|
| 데이터 모델 | 테이블 (행과 열) | 키-값, 문서, 그래프 등 |
| 스키마 | 고정 (사전 정의 필수) | 유연 (동적 변경 가능) |
| 확장 방식 | 수직 확장 중심 | 수평 확장 중심 |
| 트랜잭션 | ACID 보장 | 일부만 지원 (BASE 모델) |
| 조인 | 강력한 JOIN 지원 | 제한적이거나 미지원 |
| 일관성 | 강한 일관성 | 최종 일관성 (Eventual Consistency) |
| 응답 속도 | ms ~ 수백 ms | sub-ms ~ ms |

> **ACID vs BASE**
> - ACID: Atomicity, Consistency, Isolation, Durability — 트랜잭션의 엄격한 보장
> - BASE: Basically Available, Soft state, Eventually consistent — 가용성을 우선하고 일관성은 시간이 지나면 맞춰짐

## 1.3 NoSQL 데이터 저장소 유형

NoSQL은 데이터를 저장하는 방식에 따라 크게 네 가지 유형으로 나뉜다.

### 키-값 (Key-Value)

가장 단순한 형태의 NoSQL이다. 해시맵처럼 고유한 키에 값을 저장한다.

```
key: "user:1001:name"   →   value: "홍길동"
key: "session:abc123"   →   value: "{ userId: 1001, loginTime: ... }"
```

구조가 단순한 만큼 읽기/쓰기 속도가 가장 빠르다.

- **대표 제품**: Redis, Amazon DynamoDB, Riak
- **활용**: 캐시, 세션, 실시간 처리

### 문서 (Document)

데이터를 JSON이나 BSON 형태로 저장한다. 중첩 구조를 자유롭게 표현할 수 있다.

```json
{
  "productId": "P12345",
  "name": "노트북",
  "price": 1500000,
  "specs": {
    "cpu": "Intel i7",
    "ram": "16GB",
    "storage": ["512GB SSD", "1TB HDD"]
  },
  "tags": ["전자제품", "컴퓨터"]
}
```

- **대표 제품**: MongoDB, Couchbase
- **활용**: 상품 카탈로그, CMS, 사용자 프로필

### 칼럼 패밀리 (Column-Family)

데이터를 행이 아닌 **열 단위로 저장**한다. 수억 건의 데이터에서 특정 컬럼만 빠르게 집계할 때 유리하다.

```
Row Key: user:1001
  ├── Column Family: profile
  │     ├── name: "홍길동"
  │     └── age: "30"
  └── Column Family: activity
        ├── last_login: "2026-04-05"
        └── login_count: "142"
```

- **대표 제품**: Apache Cassandra, HBase, Google Bigtable
- **활용**: 대규모 로그, 시계열 데이터, IoT 센서 데이터

### 그래프 (Graph)

데이터를 **노드(Node)와 관계(Edge)** 로 표현한다. 관계 자체가 중요한 데이터를 다룰 때 강력하다.

```
(홍길동) ──[친구]──▶ (김철수)
   │                    │
 [좋아요]             [구매]
   │                    │
   ▼                    ▼
(게시글A)            (상품B)
```

- **대표 제품**: Neo4j, Amazon Neptune
- **활용**: 추천 시스템, 소셜 네트워크, 지식 그래프

### 유형별 비교

| 유형 | 데이터 모델 | 대표 제품 | 강점 | 주요 활용 |
|--|--|--|--|--|
| 키-값 | 키와 값 | Redis, DynamoDB | 속도 | 캐시, 세션 |
| 문서 | JSON/BSON | MongoDB | 유연성 | 카탈로그, CMS |
| 칼럼 | 칼럼 패밀리 | Cassandra, HBase | 대용량 집계 | 로그, 시계열 |
| 그래프 | 노드와 관계 | Neo4j, Neptune | 관계 탐색 | 추천, SNS |

## 1.4 레디스란?

레디스(Redis)는 **'REmote DIctionary Server'** 의 약자로, 원격에서 접근할 수 있는 사전(Dictionary) 형태의 데이터 저장소다. 2009년 살바토레 산필리포(Salvatore Sanfilippo)가 개발했으며, 현재 전 세계에서 가장 널리 사용되는 인메모리 키-값 데이터베이스다.

### 핵심 특징

**1. 인메모리 기반의 압도적 속도**

모든 데이터를 RAM에 저장한다. 디스크 기반 DB와의 속도 차이는 다음과 같다.

| 저장소 | 읽기 지연 시간 | 비유 |
|--|--|--|
| L1 캐시 | ~1 ns | 책상 위의 메모 |
| RAM (Redis) | ~100 ns | 같은 방의 책장 |
| SSD (RDBMS) | ~100,000 ns | 건물 밖의 창고 |
| HDD | ~10,000,000 ns | 다른 도시의 도서관 |

Redis가 빠른 이유는 RAM 접근 자체가 디스크보다 1,000~100,000배 빠르기 때문이다. 초당 수십만 건 이상의 명령을 처리할 수 있다.

**2. 싱글 스레드 이벤트 루프**

Redis는 **싱글 스레드**로 명령을 처리한다. 언뜻 느릴 것 같지만 오히려 장점이 된다.

- 컨텍스트 스위칭 오버헤드 없음
- 락(lock)이 필요 없어 동시성 문제 자체가 발생하지 않음
- 각 명령이 원자적(atomic)으로 실행됨

단, 오래 걸리는 명령(`KEYS *`, 큰 컬렉션의 `DEL` 등)은 전체 서버를 블로킹하므로 주의해야 한다.

```
       요청 큐
  ┌─────────────┐
  │ GET user:1  │──┐
  │ SET key val │──┤
  │ INCR count  │──┤    ┌────────────────┐
  │ ZADD rank   │──┼──▶ │  싱글 스레드    │ ──▶ 순차 처리
  │ HGET data   │──┤    │  이벤트 루프    │
  │ ...         │──┘    └────────────────┘
  └─────────────┘
```

**3. 다양한 자료구조**

단순 키-값을 넘어, String, List, Hash, Set, Sorted Set, Stream, Bitmap, HyperLogLog, GEO 등 다양한 자료구조를 제공한다. 이것이 다른 키-값 저장소와 차별화되는 가장 큰 강점이다.

> 자료구조에 대한 자세한 내용은 [Redis 자료구조 깊이 보기](/blog/redis-data-structures)에서 다룬다.

**4. 영속성 (Persistence)**

메모리 기반이지만, 데이터를 디스크에 저장하는 두 가지 방식을 제공한다.

| 방식 | 설명 | 특징 |
|--|--|--|
| RDB (스냅샷) | 특정 시점의 메모리를 통째로 덤프 | 복구 빠름, 일부 데이터 유실 가능 |
| AOF (Append Only File) | 모든 쓰기 명령을 로그로 기록 | 데이터 유실 최소화, 파일 크기 큼 |

실무에서는 **RDB + AOF를 함께 사용**하는 것이 일반적이다.

**5. 복제와 고가용성**

- **복제 (Replication)**: 마스터-슬레이브 구조로 읽기 분산
- **센티널 (Sentinel)**: 마스터 장애 시 자동 페일오버
- **클러스터 (Cluster)**: 데이터를 여러 노드에 분산 저장 (샤딩)

### 간단한 사용 예시

```bash
# 키에 값 저장
SET user:1001:name "홍길동"

# 키로 값 조회
GET user:1001:name
# → "홍길동"

# 카운터 증가
INCR article:5001:views

# 만료 시간 설정 (10분 후 자동 삭제)
SET session:abc123 "user_data" EX 600

# 해시 — 객체처럼 사용
HSET user:1001 name "홍길동" age 30 role "USER"
HGET user:1001 name
# → "홍길동"
```

## 1.5 마이크로서비스 아키텍처와 레디스

MSA 환경에서 여러 서비스가 독립적으로 동작하면서도 서로 데이터를 주고받아야 한다. 레디스는 여기서 두 가지 핵심 역할을 수행한다.

### 데이터 저장소로서의 레디스

각 서비스는 가능한 한 빠르게 응답해야 한다. 매번 RDBMS를 조회하면 디스크 I/O로 응답이 느려진다. 레디스를 **캐시 레이어**로 두면 자주 조회되는 데이터를 메모리에 보관해 응답 시간을 획기적으로 줄일 수 있다.

```
클라이언트 → 서비스 → Redis (캐시 히트?) ──Yes──▶ 즉시 응답 (< 1ms)
                          │
                          No
                          │
                          ▼
                        RDBMS ──▶ 조회 후 Redis에 저장 ──▶ 응답
```

대표적인 활용 사례:

| 역할 | 설명 | Redis 자료구조 |
|--|--|--|
| 세션 저장소 | 여러 인스턴스가 세션 공유 | Hash |
| 캐시 | 인기 상품, 검색 결과 캐싱 | String |
| 실시간 랭킹 | 게임 점수, 인기 게시물 순위 | Sorted Set |
| 분산 락 | 동시 수정 방지 | String + Lua |
| Rate Limiting | API 호출 횟수 제한 | String (INCR) |
| 카운터 | 조회수, 좋아요 수 | String (INCR) |

> 각 사용 사례의 구체적인 구현은 [Redis, 어디에 쓰이나](/blog/redis-use-cases)에서 다룬다.

### 메시지 브로커로서의 레디스

주문이 생성되면 결제 서비스와 배송 서비스에 동시에 알림을 보내야 한다. 서비스가 서로를 직접 호출하면 강하게 결합된다. 메시지 브로커를 통해 **이벤트를 발행(publish)하고 구독(subscribe)하면** 느슨하게 연결할 수 있다.

```
                        ┌─────────────────┐
                        │  Redis (브로커)   │
                        └──┬─────┬────┬───┘
                           │     │    │
  주문 서비스 ──publish──▶  │     │    │
                           │     │    │
           ┌───subscribe───┘     │    └───subscribe───┐
           ▼                     ▼                    ▼
      결제 서비스          재고 서비스            배송 서비스
```

레디스가 제공하는 메시징 기능:

| 기능 | 특징 | 적합한 상황 |
|--|--|--|
| Pub/Sub | 실시간 전달, 메시지 보관 안 됨 | 실시간 알림, 채팅 |
| List (LPUSH + BRPOP) | 간단한 큐, 1:1 소비 | 작업 큐, 백그라운드 작업 |
| Stream | 메시지 보관, Consumer Group, 순서 보장 | 이벤트 로그, 안정적 메시징 |

Kafka 같은 전용 메시지 브로커 대비 처리량은 낮지만, **이미 Redis를 사용하고 있다면 별도 인프라 없이 가벼운 메시징을 구현**할 수 있다는 것이 장점이다.

### Redis가 MSA에서 사용되는 전체 그림

```
                      ┌─────────────────────────────────────┐
                      │              Redis                   │
                      │                                     │
  ┌───────────┐       │  캐시 ← 상품 서비스                  │
  │ API       │       │  세션 ← 회원 서비스                  │
  │ Gateway   │──────▶│  분산 락 ← 주문 서비스               │
  │           │       │  Rate Limit ← API Gateway           │
  └───────────┘       │  Pub/Sub ← 서비스 간 이벤트          │
                      │  랭킹 ← 콘텐츠 서비스                │
                      └─────────────────────────────────────┘
```

## 정리

| 핵심 | 내용 |
|--|--|
| NoSQL 등장 배경 | 모놀리틱 → MSA 전환으로 다양한 데이터 형태, 빠른 응답, 수평 확장이 필요해짐 |
| NoSQL 유형 | 키-값, 문서, 칼럼, 그래프 — 문제 성격에 따라 선택 |
| Redis 정체 | 인메모리 키-값 저장소. 싱글 스레드 + 다양한 자료구조가 핵심 |
| MSA에서 역할 | 캐시, 세션, 분산 락, 랭킹, Rate Limiting + 메시지 브로커 |

다음 글에서는 Redis가 제공하는 **자료구조의 내부 인코딩과 선택 기준**을 다룬다.
